# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：
   預設直接採用盤點的 `suggest`（賣出 ＋ 沒買到），並寫出算式，例如「10 ＋ 5 ＝ 15」。
   只有使用者另外提供明天的預告或客人數資料時，才可以在 `suggest` 之上調整，而且要寫出依據與算式；沒有資料就不調整，不憑感覺多備或少備。
   每樣菜的建議都只是「單一道菜的建議」，在完成上面的可執行性檢查之前，不可以說成「已驗證的完整策略」。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：
   同一樣菜連續 2 天以上都是 `out` 或 `over`，就額外提醒：列出是哪幾天、各天的備／賣／沒買到／報廢數字，並說明這代表上一版的備貨量沒有往正確方向調整。
   只能根據盤點資料裡已有的天數提醒，不推測沒有資料的日子。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：
  可執行性檢查（下一版完整備貨）：
    總份數：各菜建議份數相加 ＝ … 份（上限 80 份，最多上架 4 樣）
    總成本：各菜（份數 × 成本單價）相加 ＝ … 元（成本單價取自規則書「菜單」）
    宣傳費：… 元（0、200、500 三選一）
    可用資金：… 元
    結論：可執行 / 不可執行（寫出超過哪一項）/ 尚無法確認可執行性（寫出缺少哪些資料）
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 我再加一條檢查：
  所有原始數字都來自使用者提供的盤點資料，或上面「資料從哪裡來」已列出的來源；自己算出來的數字（建議份數、總份數、總成本等）都列出算式。
  要判斷下一版完整備貨能不能執行，必須檢查所有餐點的總份數、總成本、宣傳費與可用資金；缺少其中任何一項，就明確寫「尚無法確認可執行性」，不下「可執行」的結論。

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 我再加一條：
  只在對話中回報分析結果：不新增、不修改任何檔案（包括策略檔、分析報告、暫存檔），也不操作遊戲（不開瀏覽器、不按遊戲按鈕）。
  不把單一道菜的建議，當成已經驗證過的完整策略。
