# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 【觀察】當天報廢合計 15 份以上；盤點裡某些菜狀態是「報廢過多」（報廢 5 份以上）。規則書：報廢 15 份清潔費 30 元，16 份起變 83 元（另加 50 元清運費）。【推測】備貨超過今天真正想買的人數；也可能是那樣菜沒人想吃或嫌太貴，需要看盤點的「賣出」「沒買到」與嫌太貴人數才能判斷 | 先看盤點：賣出 0 或很少的菜，把備貨降到「賣出 ＋ 沒買到」；仍然賣不動的菜考慮不上架。先確認是沒人想吃還是太貴，再決定要降備貨還是降價 |
| 嫌太貴很多 | 【觀察】試算的「嫌太貴」人數多（價格超過客人剩下的預算）。【推測】該菜定價超過客人預算；或客人先買了第一樣，剩下的預算不夠買第二樣，需要對照客人包的預算與想吃順序才能確定 | 只對嫌貴最多的那一樣菜小幅降價（在可定價範圍內），一次只改一樣。降價會讓每份少賺（售價 − 成本變少），所以下一版要檢查新增的購買人數有沒有補回來 |
| 想吃的沒上架很多 | 【觀察】試算的「想吃的沒上架」人數多，這些客人沒買到東西、會留下不滿評價。【推測】上架的菜和客人實際想吃的不一致；每天最多上架 4 樣，可能有想吃的菜被排除 | 對照客人包，找出被擋掉最多的菜；用「賣出 0 或報廢過多」的菜去換它（上架最多 4 樣、合計不超過 80 份）。換之前先寫下預期，下一版比較結果 |
| 因為討厭的菜不進門 | 【觀察】試算的「因為討厭的菜不進門」人數多；這些人不進店，也不留評價。【推測】某樣上架的菜是特定客人討厭的，讓這群人整天不進門，損失他們原本會買的收入 | 估算：該菜帶來的收入，對比因它而不進門的客人原本會買的收入。如果後者比較大，下一版就把那樣菜下架。要看客人包的 hates 欄位確認是誰討厭什麼 |
| 星等往下掉 | 【觀察】打烊報表顯示星等下降（例如 3 → 2.5）；規則書：滿意不到 30% 或不滿 25% 以上會扣星。【推測】不滿的人多，多半來自「什麼都沒買」（賣完、嫌太貴、沒上架）；價格超過建議售價時，買到也只算普通，不算滿意 | 先看不滿的客人是因為賣完、太貴還是沒上架，再對應調備貨、價格或上架。價格維持在建議售價以內，買到第一順位的客人才會算滿意 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | 【觀察】先核對這些數字：宣傳那天的客人數比基準日多多少；新增收入（有宣傳的營業收入 − 基準日營業收入）；備貨成本；宣傳費（200 或 500 元）；清潔費；淨利 ＝ 收入 − 備貨成本 − 宣傳費 − 清潔費。【推測】新增的客人多半沒變成收入（賣完買不到、想吃的沒上架、嫌太貴）；或新增收入還沒超過宣傳費；或備貨增加後報廢變多 | 先看新增客人有沒有買到：如果是賣完買不到，就依盤點補備貨再試；如果新增收入小於宣傳費，下一版把宣傳降回 0 元。宣傳和備貨不要同一版一起改，才知道是哪個有效 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 只能新增或修改 `web-lab/plans/` 裡的策略檔
